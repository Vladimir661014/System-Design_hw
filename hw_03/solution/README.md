## Выбранная система (контекст)

Семь backend-сервисов: **Search & Offer**, **Catalog**, **Inventory & Pricing**, **Booking**, **Payment**, **Supplier Integration**, **Notification**. Платформенные Auth / Payment service / BFF — за границей контура, своих хранилищ в этом ДЗ не проектируем.

Принцип хранения совпадает с декомпозицией ДЗ 2: у каждого bounded context — своё хранилище (Database per Service). Источник истины не дублируется: Search не владеет ценами, Catalog не владеет остатками, Booking не хранит календарь доступности.

Грубая оценка масштаба (RU-сегмент, порядок величины; точный сайзинг — ДЗ 4):

| Сущность | Оценка | Следствие для хранения |
|---|---|---|
| Объекты каталога | 10⁵–10⁶ (отели + рейсы + туры) | одна replica-set / один PG не проблема |
| Ячейки календаря | объекты × тарифы × 365 дней → 10⁸–10⁹ строк | горизонтальное хранилище, не «одна таблица PG» |
| Поиск | тысячи RPS, фасеты и полнотекст | отдельная read-модель, не SoT |
| Hold / оплата | на порядки меньше поиска | важнее ACID, чем линейный scale |
| Обновления от поставщиков | пики тысяч событий/с | write-heavy путь, буфер в Kafka |

## 1. Модель данных

Владение данными — по сервисам. Чужие агрегаты не копируем в свою БД как SoT: только снимок в read-модели Search и кэше.

ER-схема: [1_Схема_данных_по_сервисам.png](diagrams/1_Схема_данных_по_сервисам.png). Ниже — описание сущностей и связей.

### Catalog — источник истины карточки объекта

Самодостаточный агрегат «объект размещения / рейс / тур». Схема гибкая: у отеля — удобства и координаты, у рейса — маршрут и перевозчик. Обновляется редко (события `PropertyUpdated`).

| Сущность | Поля (ключевые) | Связи |
|---|---|---|
| **Property** | `id`, `type` (hotel/flight/tour), `name`, `description`, `supplier_id`, `rating`, `review_count`, `cancellation_policy`, `updated_at` | корень агрегата |
| **Location** (вложенно) | `city`, `country`, `address`, `lat`, `lng` | 1:1 с Property |
| **Photo** (вложенно) | `url`, `sort_order` | 1:N |
| **Amenity** (вложенно) | код/название | 1:N |
| **RoomType** (отель, вложенно) | `id`, `name`, `occupancy`, `beds` | 1:N; тарифы живут в Inventory |

Запросы: `GET /properties/{id}`, пакетный `GET /properties?ids=...`, фильтр по `type`. JOIN с инвентарём на стороне Catalog не нужен.

### Inventory & Pricing — остатки, цены, hold

Критичный контур: два пользователя не должны взять последний номер. Hold (10–15 мин) уменьшает остаток сразу, а не в момент confirm.

| Сущность | Поля (ключевые) | Связи |
|---|---|---|
| **AvailabilityCell** | `property_id`, `rate_plan_id`, `date`, `remaining`, `price`, `currency` | календарь; PK ячейки — тройка property/plan/date |
| **RatePlan** | `id`, `property_id`, `name`, `meal`, `refundable`, правила тарифа | N:1 к property |
| **Hold** | `id`, `property_id`, `rate_plan_id`, `check_in`, `check_out`, `user_id`, `status` (active/confirmed/released/expired), `expires_at`, `booking_id` | резервирует набор ячеек дат |
| **PromoCode** | `code`, тип скидки, значение, ограничения, срок, `usage_limit` / `usage_count` | применяется на quote |

Инвариант hold: в одной транзакции (или LWT) `remaining -= 1` по всем датам диапазона **если** везде `remaining > 0`; иначе 409. Confirm привязывает `booking_id`; expire/release возвращает остаток.

### Booking — заказ и состояние Saga

| Сущность | Поля (ключевые) | Связи |
|---|---|---|
| **Booking** | `id`, `user_id`, `hold_id`, `property_id`, `rate_plan_id`, `status`, `check_in`/`check_out`, `total_price`, `currency`, `payment_id`, `supplier_confirmation_id`, timestamps | корень; статусы как в ДЗ 2 |
| **Guest** | ФИО, email, phone | 1:N, принадлежат брони |
| **SagaState** | текущий шаг, компенсации, `idempotency_key` | 1:1 с Booking (можно колонками на Booking) |
| **OutboxEvent** | `event_id`, payload, `created_at`, `published_at` | Transactional Outbox |
| **IdempotencyRecord** | ключ, ответ, TTL | защита retry |

Booking хранит снимок цены и `property_id` на момент заказа (чтобы карточка заказа не «поехала» после смены тарифа), но не календарь остатков.

### Payment — журнал операций

PAN/реквизиты карты не храним — только токен провайдера и суммы.

| Сущность | Поля (ключевые) |
|---|---|
| **Payment** | `id`, `booking_id`, `amount`, `currency`, `method`, `status`, `provider_ref`, `idempotency_key` |
| **Refund** | `id`, `payment_id`, сумма (полная/частичная), статус, `provider_ref` |
| **OutboxEvent** | как в Booking — `PaymentSucceeded` / `RefundCompleted` |

### Search & Offer — read-модель (не SoT)

Собственной write-БД нет. Проекция в поисковый индекс:

| Документ | Поля | Откуда |
|---|---|---|
| **OfferDocument** | `property_id`, `type`, `name`, `geo`, `amenities`, `rating`, `min_price`, `currency`, `availability_bitmap` / вложенные даты, `thumbnail_url` | Catalog + Inventory через Kafka |

`offer_id` на выдаче — детерминированный идентификатор проекции (property + тариф + даты), не отдельная сущность SoT.

### Supplier Integration — антикоррупционный слой

| Сущность | Назначение |
|---|---|
| **Partner** | поставщик, протокол, endpoint, секреты (encrypted), SLA |
| **IdMapping** | `(supplier_id, external_id) → property_id` / `rate_plan_id` |
| **WebhookInbox** | сырой payload, `event_id` поставщика, статус обработки (идемпотентность) |
| **OutboundCommand** | confirm/cancel к поставщику, retry, correlation с `booking_id` |

### Notification

Своего доменного SoT нет: шаблоны — в конфиге/object storage, доставка — fire-and-forget. Краткоживущие ключи дедупликации «это `event_id` уже отправляли» — в Redis. История писем в личном кабинете маркетплейса — не наш контур.

### Границы владения (чтобы не размазать SoT)

```
Catalog.Property          ──snapshot──► Search.OfferDocument
Inventory.AvailabilityCell ──snapshot──► Search.OfferDocument
Inventory.Hold            ──ref hold_id──► Booking
Booking                   ──ref booking_id──► Payment
Supplier.IdMapping        ──связка──► Catalog.property_id
```

## 2. Выбор БД

Не «PostgreSQL везде»: тип хранилища следует из формы данных и запросов. Операционную стоимость учитываем — шесть разных СУБД не плодим; четыре семейства + Redis как кэш покрывают паттерны.

### Таблица выбора

| Сервис | Что хранит | Форма данных | Ключевые запросы | Выбранная БД | Почему именно она |
|---|---|---|---|---|---|
| **Search & Offer** | проекция офферов | инвертированный индекс | полнотекст, фасеты (цена, звёзды, удобства), geo, сортировка | **OpenSearch** | запросы поиска — не точечный GET и не JOIN; near-real-time и eventual на выдаче допустимы |
| **Catalog** | карточка объекта | JSON-агрегат, вложенные фото/удобства/гео | GET по `id`, batch по ids | **MongoDB** | документ = агрегат Property; разные формы hotel/flight/tour без широких ALTER; JOIN не нужны |
| **Inventory & Pricing** | календарь остатков/цен, hold | wide-column: строка property, колонки/кластеры по дате; hold — короткий TTL | запись потока поставщика; чтение диапазона дат; атомарный decrement | **ScyllaDB** (календарь + hold) | write-heavy 10⁸+ ячеек, запросы всегда по `property_id` + даты; TTL hold нативно; LWT/`IF remaining > 0` на последнем номере |
| **Booking** | заказ, гости, Saga, outbox | реляционная, транзакции | по `id`, список по `user_id`, смена статуса + outbox атомарно | **PostgreSQL** | ACID на оформлении; Outbox в той же транзакции; гибкие фильтры поддержки |
| **Payment** | платежи, возвраты, идемпотентность | реляционная, журнал сумм | по `id` / `booking_id`, unique `idempotency_key` | **PostgreSQL** | деньги: строгая целостность, уникальность ключа, нет смысла в документной модели |
| **Supplier Integration** | партнёры, маппинг id, inbox webhook | связи + идемпотентные записи | lookup `(supplier, external_id)`, дедуп webhook | **PostgreSQL** | маппинг — классическая связь; unique на inbound `event_id`; объём умеренный |
| **Notification** | дедуп доставки | ключ → TTL | «уже слали этот event?» | **Redis** | нет доменной модели; достаточно ephemeral key с TTL |

Кэш (**Redis**) — общий слой чтения, не SoT (кроме эфемерной дедупликации Notification). Подробнее в §4.

### Почему так, а не иначе

**Search → OpenSearch, не PostgreSQL/Mongo.** `ILIKE` и GIN не заменят фасеты, relevance и geo-distance на тысячах RPS. Индекс — проекция CQRS из ДЗ 2, не источник истины: цена в выдаче может отстать на секунды.

**Catalog → MongoDB, не PostgreSQL JSONB.** JSONB был бы рабочим, но тогда три сервиса подряд на PG без выигрыша. Каталог — типичный документный агрегат без кросс-документных транзакций. Чем жертвуем: нет JOIN «отель + все брони» (их и не должно быть в Catalog).

**Inventory → ScyllaDB, не PostgreSQL.** Календарь — не OLTP-заказы, а огромный поток ячеек и обновлений от Kafka. PG вертикально вывезет hold/confirm (редкие), но не будет удобной моделью для 10⁸–10⁹ ячеек и пишущей синхронизации. Чем жертвуем: нет произвольных JOIN и вторичных индексов «все отели города с remaining > 0» — это задача OpenSearch, не Inventory. Атомарность hold — через LWT (Paxos на партицию), не через MVCC всего кластера.

**Почему не Redis как SoT остатков.** Sub-ms и TTL hold соблазнительны, но потеря записи при failover = овербукинг. Redis оставляем кэшем. Hold в Scylla с `USING TTL` переживает рестарт узла.

**Booking и Payment → PostgreSQL, два отдельных инстанса.** Одинаковое семейство — нормально: оба требуют ACID. Это не «одна БД на всю систему»: разные кластеры, разные схемы, связь только по id через API/события. NewSQL (Cockroach/Yugabyte) не берём: операционная цена не окупается, пока шардирование PG по `user_id` не исчерпано.

**Не берём:** граф (нет обхода соцсвязей в критическом пути), ClickHouse (нет OLAP в контуре бронирования), Timescale (нет метрик как домена), DynamoDB (нет привязки к AWS как обязательному облаку).

## 3. Шардирование

Шардируем то, что не влезет в одну ноду **по данным или по записи**. Catalog (~10⁶ документов) и Payment (соизмерим с Booking, но уже PG) на старте — replica set / primary+replicas. Search шардируется движком OpenSearch (по `property_id`) — отдельно не проектируем.

Два ключевых контура: **Inventory (нужно сразу)** и **Booking (план роста)**.

### 3.1. Inventory & Pricing (ScyllaDB) — нужно сразу

**Почему шардировать:** 10⁸–10⁹ ячеек календаря + пишущий поток поставщиков. Вертикальный PG + кэш не являются целевой моделью этого объёма. Реплики Scylla закрывают чтение; шарды (vnode) — запись и размер.

#### Выбор ключа

| Кандидат | Равномерность | Локальность запросов | Риск hotspot | Вывод |
|---|---|---|---|---|
| `property_id` | высокая на длинном хвосте | диапазон дат одного отеля — один шард; hold по объекту локален | популярные отели (центр Москвы) | **берём как partition key** |
| `date` | плохая | hold на 5 ночей = 5 шардов | «ближайшие выходные» — глобальный hotspot | нет |
| `city` / `destination` | плохая | поиск по городу был бы локальным, но поиск идёт в OpenSearch | Москва/Сочи | нет |
| `user_id` | высокая | календарь не про пользователя | — | нет, не тот access pattern |
| `(property_id, rate_plan_id)` | ещё ровнее | quote по всем тарифам отеля — scatter внутри отеля | снижает hotspot одного отеля | запасной ключ, если один property не влезает |

**Ключ:** `PARTITION KEY (property_id)`, clustering `(rate_plan_id, date)`.

Типовой запрос «остаток и цена на check-in…check-out» и hold на диапазон дат идут в **один шард**. Search не сканирует все шарды Inventory — он читает OpenSearch.

**Стратегия:** hash-партиционирование Scylla (consistent hashing + vnode). Не range по дате — иначе «сегодня» всегда горячий шард.

**Старт:** 6 узлов × 3 DC-реплика (RF=3), quorum R/W. Число vnode стандартное; pre-split не нужен — token ring сам размазывает `property_id`.

**Ребалансировка:** добавление узла — Scylla streaming части vnode, без `% N` вручную. Простой записи на горячем токене краткий; клиент ретраит. Долю ключей, которые переедут, оцениваем как `1/(n+1)` токенов.

**Hold и LWT:** `UPDATE remaining = remaining - 1 IF remaining > 0` на ячейках диапазона. LWT сериализуется **внутри партиции** `property_id` — это как раз граница, где нужна атомарность «последний номер». Распределённая транзакция на несколько отелей не нужна.

#### Риски Inventory

| Риск | Как лечим |
|---|---|
| Hotspot популярного отеля | мониторинг размера партиции; split ключа на `(property_id, rate_plan_id)` только для этих id (directory исключений) |
| Cross-shard | не строим запросы «все остатки города» к Scylla — это OpenSearch |
| Вторичные индексы | не используем глобально; lookup hold по `hold_id` — отдельная таблица `holds` с PK `(hold_id)` + данные `property_id` (два ключа, запись в обе в приложении) |
| TTL hold vs decrement | expire по TTL **и** компенсирующий consumer: если статус не `confirmed`, вернуть `remaining` идемпотентно (иначе гонка TTL + confirm) |

Таблица `holds`: PK `(hold_id)` — точечный GET/DELETE с BFF; поля `property_id`, даты, статус. При создании hold пишем ячейки календаря + строку hold (два запроса, идемпотентно по `hold_id`).

### 3.2. Booking (PostgreSQL) — на старте не обязательно, схема готова к росту

**Почему можно не шардировать сразу:** число заказов растёт линейно с успешными оплатами, не с поиском. Один primary PG + read-replica на «мои брони» выдержит долго (миллионы строк — комфортный PG).

**Почему проектируем ключ заранее:** когда появятся десятки ТБ архива и write-RPS в сотни, перенос без ключа больнее, чем заложить `user_id` в идентификатор сейчас.

#### Выбор ключа

| Кандидат | Равномерность | Локальность | Hotspot | Вывод |
|---|---|---|---|---|
| `booking_id` (hash) | высокая | GET по id — один шард; «мои брони» — scatter-gather | низкий | плохо под главный список |
| **`user_id`** | высокая (B2C) | список броней пользователя локален; Saga/гости/outbox — тот же шард | корпоративный «бот»/агентство | **берём** |
| `created_at` range | hotspot на «сейчас» | удобно архивировать | пик праздников | нет как shard key |
| `property_id` | перекос на популярные отели | «все брони отеля» локальны, но это не наш UI | да | нет |

**Ключ:** hash(`user_id`). **Стратегия на старте:** один шард (logical). **При росте:** consistent hashing / Citus-like distribution по `user_id`.

`booking_id` кодирует hint шарда (префикс токена `user_id`), чтобы `GET /bookings/{id}` без `user_id` не ходил в directory. Поддержка «найти по фамилии гостя» — редкий scatter-gather или отдельный индекс в OpenSearch для support, не OLTP-путь.

**Старт:** 1 primary + 1 replica. План: 4 шарда, когда write primary упрётся в CPU/диск (ориентир — ДЗ 4).

**Ребалансировка:** новые пользователи на новые шарды; старые бакеты переезжают батчами (dual-write / reshard tool). Простой — read-only на бакете на минуты, не глобальный даунтайм.

**Транзакции:** Booking + Guest + Outbox всегда с одним `user_id` → один шард. Payment — другой сервис (Saga), 2PC нет.

**Cross-shard:** нет бизнес-сценария «одна бронь на двух пользователей». Отмена и pay идут в шард владельца.

Схемы: [2_Схема_шардирования_Inventory.png](diagrams/2_Схема_шардирования_Inventory.png) (данные → ключ → шарды) · [2b_Типовой_запрос_hold.png](diagrams/2b_Типовой_запрос_hold.png) (hold остаётся на одном шарде).

### Итоговая схема шардирования

| Сервис | Что шардируем | Ключ | Стратегия | Кол-во шардов (старт) | Ребалансировка | Главный риск + как лечим |
|---|---|---|---|---|---|---|
| **Inventory** | календарь остатков/цен, hold | `property_id` | consistent hashing (Scylla vnode) | 6 узлов, RF=3 | streaming vnode, без ручного `% N` | hotspot отеля → split `(property_id, rate_plan_id)` |
| **Booking** | заказы, гости, outbox | `user_id` | hash; на старте 1 шард | 1 (+ replica) | добавление шардов + переезд бакетов | GET без user → shard hint в `booking_id` |

Типовые запросы:

- Hold номера: hash(`property_id`) → один узел Scylla → LWT по датам диапазона.
- «Мои брони»: hash(`user_id`) → один PG.
- Поиск «отели в Казани на даты»: **не** Inventory и **не** Booking — OpenSearch (свои шарды по документу property).

## 4. Кэширование

Кэшируем то, что **часто читают, редко меняют и дорого доставать**. Не кэшируем то, где устаревание даёт овербукинг или неверный списанный платёж.

### Что кэшируем

| Что кэшируем | Уровень | Стратегия | TTL | Инвалидация | Зачем |
|---|---|---|---|---|---|
| Карточка Property | Redis (app) | cache-aside | 15 мин | событие `PropertyUpdated` → `DEL catalog:property:{id}` | Search и BFF бьют одну карточку много раз; Catalog не должен держать QPS поиска |
| Пакет properties по ids | Redis | cache-aside | 15 мин | по каждому id из события | тот же выигрыш на агрегации Search |
| Фото объектов | CDN | cache-aside / HTTP cache | 24 ч (immutable URL с hash в пути) | смена URL при новом файле | статика, география, не грузим origin |
| Выдача поиска по ключу запроса | Redis | cache-aside | **45 с** | только TTL (цены живут своей жизнью) | одинаковые «Москва, ближайшие выходные, 2 взрослых» в пике; короткая свежесть |
| OfferDocument в OpenSearch | сам индекс | проекция (write из Kafka) | n/a (near-real-time) | событие Inventory/Catalog переиндексирует документ | это не кэш поверх SoT, а CQRS read-модель |
| Rate plan / политика отмены | Redis | cache-aside | 10 мин | update тарифа | редко меняется, читается на карточке и quote |
| Маппинг `external_id → property_id` | Redis | cache-aside | 1 ч | invalidate при изменении IdMapping | горячий путь webhook'ов поставщика |
| Дедуп Notification `event_id` | Redis | write-through ключа | 48 ч | истечение TTL | не SoT, защита at-least-once |

Ключ поиска: `search:{type}:{destination}:{check_in}:{check_out}:{adults}:{children}:{sort}:{filters_hash}`. Слишком широкий ключ (с `user_id`) раздует кэш персонализацией — персональный rerank поверх общего закэшированного списка, не отдельная копия на пользователя.

### Что сознательно не кэшируем

| Данные | Почему |
|---|---|
| Остаток на **checkout / POST /holds** | last-room: stale «есть места» → 409 всё равно лучше, чем овербукинг; hold идёт в Scylla |
| Статус брони в `processing` | клиент ждёт SSE, не кэш; смена confirmed/rejected должна быть мгновенной |
| Платёж, refund, idempotency Payment | деньги; источник — PG |
| Активный Hold как «можно показать в поиске как занято» через длинный кэш выдачи | именно поэтому TTL поиска 45 с, а не 15 мин |

Write-behind (писать только в кэш, в БД асинхронно) **не используем** ни для остатков, ни для заказов — риск потери при падении Redis.

### Инвалидация, stale, stampede

- **Catalog:** событие + TTL. Допустимо показать описание отеля старше на минуты; цена в карточке оффера берётся из проекции Search/Inventory, не из кэша описания.
- **Поиск:** только короткий TTL. Явная инвалидация всех ключей «Москва» при одном `PriceUpdated` дороже, чем 45 с stale. Пользователь на выдаче видит near-real-time; на hold получает актуальный ответ.
- **Stampede:** на промахе популярного `search:...` — singleflight (один запрос в OpenSearch на ключ, остальные ждут). Для карточки Property — lock ключа `lock:catalog:{id}` на 1–2 с.
- **Cold start:** OpenSearch — тёплая read-модель (живёт отдельно от Redis). Redis наполняется с трафика. Опционально warmup топ-направлений после выката (не блокирует старт).
- **Вытеснение:** LRU + TTL; память под выдачу ограничена (короткий TTL сам чистит). Карточки Property — LFU предпочтительнее, если метрики покажут длинный хвост id.

## 5. Очереди

Брокер уже выбран в ДЗ 2: **Apache Kafka**. Здесь — зачем именно он в модели хранения и какие топики/гарантии стыкуются с БД.

### Где брокер обязателен

| Поток | Топик (логически) | Producer | Consumer | Зачем очередь, а не RPC |
|---|---|---|---|---|
| Синхронизация инвентаря | `inventory.availability`, `inventory.prices` | Supplier Integration | Inventory (Scylla), Search (индексация) | пики тысяч обновлений/с; буфер; Inventory пишет в своём темпе |
| Статика каталога | `catalog.properties` | Supplier Integration | Catalog, Search | не критический путь; fan-out в две read/write модели |
| Жизненный цикл брони | `booking.events` | Booking (outbox) | Notification, контур заказов, SSE-мост | не держать HTTP до push/email |
| Платежные факты | `payment.events` | Payment (outbox) | Booking (компенсации/сверка), Notification | webhook провайдера и refund — асинхронные факты |
| Confirm поставщика | `supplier.booking-results` | Supplier Integration | Booking | ответ отеля 5–60 с |
| Напоминание о заезде | `booking.reminders` (delay) | Booking | Notification | факт в будущем, без cron в монолите |

### Почему Kafka, а не RabbitMQ / SQS / «просто Redis list»

| Требование | Kafka | Почему не альтернатива |
|---|---|---|
| Пик синхронизации инвентаря | последовательная запись в партиции, disk-backed | RabbitMQ хуже как буфер большого backlog на часы |
| Replay при баге индекса Search | retention + consumer group с reset offset | очередь с ack-удалением не даст переиграть сутки цен |
| Порядок статусов одной брони | ключ партиции `booking_id` | конкурирующие consumer'ы без ключа перепутают confirmed/cancelled |
| Несколько независимых читателей | fan-out consumer groups | конкурирующая очередь отдала бы сообщение одному |
| Outbox → брокер | простой relay, идемпотентный produce | |

Redis как очередь **не используем**: нет долгого retention и нормального replay. Redis — кэш и дедуп.

### Связь с хранилищами

- **Transactional Outbox** в PostgreSQL Booking и Payment: строка outbox в той же транзакции, что статус; relay публикует в Kafka. Так хранилище и брокер не расходятся («commit брони, crash до produce»).
- **Идемпотентные consumer'ы:** `event_id` в Scylla/PG/Redis. Kafka — at-least-once.
- **Партиции:** `booking_id` — события заказа; `property_id` — обновления инвентаря (порядок цен одного отеля сохраняется, шарды Search/Inventory совпадают по ключу).
- **DLQ:** `*.dlq` после N ретраев (битый маппинг поставщика, вечный 5xx). Ручной разбор, не молчаливый drop.
- **Expire hold:** не полагаемся только на Kafka delay — TTL в Scylla + reconciler (скан истекших `active`). Очередь напоминаний — отдельно.

### Что очередью не делаем

Синхронные hold, charge, чтение поиска — остаются gRPC/REST. Кладём в Kafka только факты, для которых вызывающему не нужен результат «прямо сейчас», чтобы продолжить сценарий (критерий из ДЗ 2).

## 6. CAP trade-offs

В сети с разделением нельзя одновременно дать строгую консистентность и полную доступность. Выбор — **по операции**, не «кластер целиком AP или CP».

### Карта решений

| Контур | Выбор | Что сохраняем при partition | Чем жертвуем | Почему допустимо |
|---|---|---|---|---|
| Hold / remaining (Scylla LWT, quorum) | **CP** | один согласованный остаток | 503, если нет кворума | лучше не продать, чем овербукинг |
| Booking write (PG primary) | **CP** | один статус заказа | недоступна запись без primary | двойная бронь хуже, чем «попробуйте снова» |
| Payment write | **CP** | нет двойного списания (`idempotency_key`) | запись недоступна | деньги |
| Search / OpenSearch | **AP** | выдача живёт на доступных шардах | stale цена/остаток секунды–минуты | пользователь ещё не платит; hold перепроверит |
| Кэш Redis карточек | **AP** | отдать старую карточку | расхождение с Mongo | описание отеля не last-room |
| Catalog Mongo (majority write, secondary read) | запись **CP**, чтение карточки можно **AP** | | вторичные могут отстать | для карточки ок; админский upsert ждёт majority |
| Notification | **AP** | пуш позже / повтор | дубликат письма ловит дедуп | не критический путь |
| Kafka | **AP** внутри ISR: пишем, пока есть лидер партиции | при потере ISR — недоступна партиция (скорее CP на min.insync) | `min.insync.replicas=2`, `acks=all` на booking/payment; для inventory-событий можно ослабить | заказ важнее, чем одна потерянная цена — её пришлют следующим обновлением |

### Сценарии

**1. Потеря связи с кворумом Scylla в DC.** Hold и confirm перестают писать (CP). Поиск продолжает отдавать OpenSearch (AP) — пользователь видит выдачу, на оформлении получает ошибку «временно нельзя забронировать», а не подтверждение на уже проданный номер.

**2. Падение primary Booking PG.** Чтение «моих броней» с replica (возможна задержка репликации — оговариваем). Создание брони и pay — недоступны, failover по replica promotion. Не переключаемся на «запись в любой узел» (мультимастер): конфликт статусов Saga дороже простоя записи.

**3. Рассинхрон Kafka → Search.** Выдача показывает цену на 10 с старше. Это **eventual consistency** read-модели, заложенная в CQRS. Инвариант last-room держит Inventory на hold, не поиск.

**4. Split-brain Redis.** Кэш можно потерять целиком: источник — Mongo/OpenSearch. Запрещено делать Redis кворумным SoT остатков.

### Сводка инвариантов

- **Сильная согласованность:** остаток при hold, статус оплаты, переход статусов брони на записи.
- **Eventual:** поисковая выдача, карточка каталога в кэше, пуш, заказ в личном кабинете маркетплейса, календарь Search относительно поставщика.
- **Компенсация вместо 2PC:** если после CP-записи оплаты AP-путь поставщика отверг бронь — refund + release hold (Saga из ДЗ 2). Хранилища не пытаются дать распределённый commit на три системы.

Этим закрывается критерий CAP: где пользователю нужна правда (деньги, последний номер) — жертвуем доступностью записи; где нужна живая витрина — жертвуем строгостью на секунды и проверяем правду на следующем шаге оформления.
