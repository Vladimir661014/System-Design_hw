## Выбранная система

**Cервис бронирования** — сервис бронирования отелей, авиабилетов и смежных travel-услуг (аналог Ozon Travel/ Яндекс Путешествия/ Booking / Airbnb...).

## 1. Декомпозиция

**Cервис бронирования** — маркетплейс бронирования отелей, авиабилетов и смежных travel-услуг. Пользователь может найти предложения, забронировать их и оплатить, а так же может управляеть заказом.
Поставщики (отели, авиакомпании, агрегаторы, туроператоры...) подтверждают наличие, бронируемых позиций и принимают изменения. Ключевые сложности: актуальный информация, единовременное бронирование одного номера/билета разными пользователями, распределённая оплата (процессинг отменамы и/или возвратама), интеграция с внешними сервисами.

**Описание сервисов и составление схем буду производить, опираясь на RU сегмен (за основу взяты Ozon Travel + Яндекс Путешествия). 

Ниже — **7 основных backend-сервисов** travel-контура клиент, API Gateway, Auth (Ozon ID/Yandex Pasport, Payment service (Ozon Pay/Yandex Pay) — вынесены за границу как платформенные сервисы). Разделение по bounded context: поиск отделён от инвентаря, бронирование — от платежей, синхронная выдача — от асинхронной работы с поставщиками.

**Сервис поиска и выдачи (Search & Offer)**  
Тип: сервис  
Зона ответственности: приём поисковых запросов (отель, рейс, тур; даты, гости, фильтры), агрегация предложений из инвентаря и каталога, ранжирование с учётом персонализации. Не владеет ценами и остатками — читает снимки у Inventory и метаданные у Catalog.

**Сервис каталога (Catalog)**  
Тип: сервис  
Зона ответственности: статические и полустатические данные об отелях, рейсах и турах — название, маршрут, фото, удобства, политики отмены, рейтинги. Обновляется реже доступности; источник правды для карточки предложения в UI.

**Сервис инвентаря и цен (Inventory & Pricing)**  
Тип: сервис  
Зона ответственности: доступность номеров, мест и туров по датам, тарифные планы, динамические цены, промокоды и скидки. Рассчитывает итоговую цену с учётом баллов лояльности и рассрочки (запрашивает условия у платформенного сервиса лояльности). Создаёт **временную блокировку (hold)** на 10–15 минут при оформлении. Критичен к консистентности: два пользователя не должны забронировать один и тот же последний номер или билет.

**Сервис бронирования (Booking)**  
Тип: сервис  
Зона ответственности: жизненный цикл travel-заказа — создание, подтверждение, изменение, отмена. Оркестрирует сценарий «hold → оплата → подтверждение у поставщика» (Saga); хранит статусы брони и данные гостей. Публикует события в общий контур заказов, чтобы travel-бронь отображалась рядом с покупками маркетплейса. Платежи и синхронизация с поставщиками — через отдельные сервисы.

**Сервис платежей (Payment)**  
Тип: сервис  
Зона ответственности: списание, предавторизация, захват средств, рассрочка, возвраты и частичные возвраты при отмене. Идемпотентные операции со связкой на заказ в Booking. Интеграция с **Payment service**.

**Сервис интеграции с поставщиками (Supplier Integration)**  
Тип: сервис  
Зона ответственности: адаптеры к отелям, channel manager'ам, GDS, авиакомпаниям и туроператорам. Подтверждение и отмена брони у поставщика, приём webhook'ов об изменении инвентаря и цен, периодическая синхронизация. Изолирует разнородные протоколы партнёров от внутренней доменной модели Ozon Travel.

**Сервис уведомлений (Notification)**  
Тип: сервис  
Зона ответственности: доставка push (в приложении), email и SMS по событиям жизненного цикла заказа — подтверждение, напоминание о заезде или вылете, отмена, возврат. Работает асинхронно по событиям из брокера; не участвует в критическом пути оплаты и подтверждения.

## 2. Протоколы

Принцип: под каждый тип взаимодействия — свой протокол. Синхронные команды на критическом пути (hold, оплата) — gRPC; публичный API для клиента — REST; факты о произошедшем — события через брокер.

### Сводная таблица

| Откуда → Куда | Протокол | Сценарий |
|---|---|---|
| Клиент → API Gateway (BFF) | **REST** | Поиск (`GET /search`), карточка предложения (`GET /offers/{id}`) — BFF агрегирует Catalog + Inventory |
| Клиент → API Gateway (BFF) | **REST** | Оформление брони, оплата, отмена — идемпотентные команды, простой контракт |
| Клиент ← API Gateway | **SSE** | Ожидание подтверждения брони у поставщика (статус «обрабатывается» → «подтверждено») |
| Search & Offer → Catalog, Inventory | **gRPC** | Параллельное чтение метаданных и цен; latency-бюджет поиска — сотни миллисекунд |
| Booking → Inventory & Pricing | **gRPC** | Hold / confirm / release — синхронно, строгий контракт, консистентность |
| Booking → Payment | **gRPC** | Списание и возврат в рамках Saga; идемпотентные вызовы по `idempotency_key` |
| Booking → Supplier Integration | **gRPC** | Команды «подтвердить» / «отменить» у поставщика |
| Supplier Integration → внешние партнёры | **REST** | Разнородные HTTP API отелей, GDS, туроператоров; webhook'и от партнёров |
| Supplier Integration → Inventory & Pricing | **Events (Kafka)** | Поток обновлений доступности и цен; буфер пиков синхронизации |
| Booking → Notification, контур заказов | **Events (Kafka)** | `BookingConfirmed`, `BookingCancelled`, `PaymentRefunded` — развязка по времени |
| Payment → Payment service (Ozon Pay / Yandex Pay) | **REST** | Внешний платёжный провайдер; стандартная HTTP-интеграция |
| Catalog ← Supplier Integration | **Events (Kafka)** | Обновление статики (фото, описание, политики) — не на критическом пути |

### REST — публичный API (BFF)

**Где:** клиент (web / mobile) → API Gateway (BFF) → Search & Offer, Catalog, Inventory, Booking, Payment.

**Почему:** единый HTTP-контракт для чтения и записи. BFF агрегирует данные из внутренних сервисов и отдаёт клиенту готовые DTO:
- `GET /search` — поиск с фильтрами; BFF параллельно запрашивает Search, Catalog, Inventory и собирает ответ;
- `GET /offers/{id}` — карточка отеля/тура с ценой и доступностью;
- `POST /bookings`, `POST /bookings/{id}/pay`, `POST /bookings/{id}/cancel` — команды жизненного цикла заказа.

REST нативно поддерживается браузером и мобильными SDK, легко кэшируется на CDN для статики каталога, проще версионировать (`/v1/...`) и отлаживать (curl, OpenAPI). Идемпотентные команды удобны для retry на клиенте. Webhook'и от платёжного провайдера — тоже REST (`POST /payments/callback`).

**Trade-off:** при поиске BFF может сделать несколько внутренних вызовов вместо одного GraphQL-запроса — компенсируем параллельными gRPC-вызовами к Catalog и Inventory; overfetching на клиенте не критичен, т.к. BFF отдаёт уже собранный ответ.

### gRPC — синхронное межсервисное взаимодействие

**Где:** Search → Catalog / Inventory; Booking → Inventory / Payment / Supplier Integration.

**Почему:**
- **Search → Catalog / Inventory** — при выдаче результатов BFF/Search делает десятки параллельных чтений; Protobuf компактнее JSON, HTTP/2 мультиплексирует запросы, `.proto` даёт строгую типизацию между командами на разных языках.
- **Booking → Inventory** — hold должен ответить за < 100 ms, иначе пользователь уходит; нужна атомарная семантика «заблокировать или отказать».
- **Booking → Payment** — Saga-оркестрация: синхронный вызов «списать» с немедленным ответом success/fail; при fail — компенсирующий release hold.
- **Booking → Supplier Integration** — команда подтверждения с таймаутом; gRPC deadline передаётся по цепочке.

**Почему не REST внутри:** выше latency, слабее контракт; gRPC не подходит для браузера — поэтому только backend-to-backend.

### Events (Kafka) — асинхронная развязка

**Где:**
- Supplier Integration → Inventory & Pricing — `AvailabilityChanged`, `PriceUpdated`
- Supplier Integration → Catalog — `PropertyUpdated`
- Booking → Notification — `BookingConfirmed`, `BookingCancelled`, `CheckInReminder`
- Booking → контур заказов маркетплейса — `OrderCreated`, `OrderStatusChanged`
- Payment → Booking — `PaymentSucceeded`, `PaymentFailed`, `RefundCompleted`

**Почему:** поставщики присылают тысячи обновлений цен и остатков — синхронная запись в Inventory перегрузит сервис. Брокер буферизует пики, гарантирует at-least-once доставку, позволяет Inventory обрабатывать в своём темпе. Уведомления и публикация в личный кабинет не должны блокировать ответ пользователю «бронь принята» — событие уходит в Kafka, Notification доставит push/email когда сможет.

**Семантика:** at-least-once + идемпотентные consumer'ы (дедупликация по `event_id`).

### SSE — статус брони в реальном времени

**Где:** клиент ← API Gateway / Booking.

**Почему:** после оплаты подтверждение у поставщика может занять 5–30 секунд. Вместо polling каждые 2 с клиент открывает SSE-подписку на `bookings/{id}/status` и получает push при смене статуса (`processing` → `confirmed` / `rejected`). SSE проще WebSocket: однонаправленный поток server→client, нативная поддержка в браузере, автоматический reconnect.

**Почему не WebSocket:** двусторонний канал не нужен — клиент не шлёт данные в процессе ожидания.

### Что сознательно не используем

| Протокол | Причина |
|---|---|
| **GraphQL** | агрегацию берёт на себя BFF; для web/mobile достаточно REST + готовые DTO; меньше операционной сложности |
| **MQTT** | нет IoT/телеметрии; клиенты — web/mobile с HTTP |
| **WebSocket** | для статуса брони достаточно SSE; чат с поддержкой — отдельный контур |

## 3. Схема взаимодействия

Три схемы покрывают основной сценарий бронирования, фоновую синхронизацию данных от поставщиков и машину состояний Saga. На рёбрах указаны протоколы: **REST** (клиент ↔ BFF), **gRPC** (межсервисный критический путь), **SSE** (статус брони), **Events/Kafka** (асинхронная развязка).

### 1. Основной поток бронирования [1_Cхема_взаимодействия_(основной поток бронирования).png](diagrams/1_Cхема_взаимодействия_(основной%20поток%20бронирования).png)

Сквозная sequence-диаграмма happy path и веток ошибок на критическом пути:

1. **Критический путь (синхронно, gRPC):** клиент → BFF (`REST POST /bookings`) → Booking → Inventory (`hold`) → Payment (`charge`) → Supplier Integration (`confirm` у поставщика по REST).
2. **Ветвления:** hold не удался → `409`; оплата не прошла → `release hold` + `402`; оплата прошла → `202 Accepted` + SSE-подписка на статус.
3. **Асинхронные потоки (Kafka):** обновления инвентаря от Supplier Integration, события `BookingConfirmed` / `PaymentSucceeded` / `RefundCompleted`, доставка уведомлений через Notification (retries + DLQ — сбой доставки не откатывает бронь).

Показывает сочетание синхронных команд на пути пользователя и событийной развязки для всего, что не блокирует ответ клиенту.

### 2. Синхронизация инвентаря от поставщиков [2_Схема_потока_синхронизации_инвентаря_(от поставщиков).png](diagrams/2_Схема_потока_синхронизации_инвентаря_(от%20поставщиков).png)

Отдельная схема фонового потока данных — не на критическом пути бронирования:

1. Поставщик (channel manager / GDS / отель) шлёт обновления в Supplier Integration через **webhook или polling (REST)**.
2. Supplier Integration публикует в Kafka: `AvailabilityChanged`, `PriceUpdated`, `PropertyUpdated`.
3. **Inventory & Pricing** и **Catalog** потребляют события независимо, в своём темпе (пакетная обработка).

Задержка между изменением у поставщика и отображением в поиске допустима (**eventual consistency**); брокер буферизует пики синхронизации.

### 3. Saga — оркестрация и компенсации [3_Схема_для_Saga_(оркестрация и компенсации).png](diagrams/3_Схема_для_Saga_(оркестрация%20и%20компенсации).png)

Диаграмма состояний распределённой транзакции; оркестратор — **Booking**:

| Шаг | Успех | Ошибка → компенсация |
|---|---|---|
| **Hold** | → Payment | → отмена (конец сценария) |
| **Payment** | → Confirm | → ReleaseHold |
| **Confirm** | → Complete | → Refund → ReleaseHold |

Состояния брони в Booking: `pending_payment` → `processing` → `confirmed` / `rejected` / `cancelled`. Все команды идемпотентны по `idempotency_key` — безопасный retry при сетевых сбоях и повторной доставке Kafka.

## 5. Асинхронность

Граница синхронного и асинхронного взаимодействия проводится по вопросу: **должен ли вызывающий получить результат прямо сейчас, чтобы продолжить сценарий?** Если да — синхронный вызов (gRPC/REST). Если нет — событие в Kafka; потребитель обработает позже.

### Синхронно vs асинхронно по сценариям

| Сценарий | Режим | Почему |
|---|---|---|
| Поиск и карточка предложения | **Синхронный** | Пользователь ждёт результат на экране; latency-бюджет < 1 с |
| Hold номера при оформлении | **Синхронный** | Нужен немедленный ответ «заблокировано / нет мест» |
| Списание оплаты | **Синхронный** | Без подтверждения оплаты нельзя переходить к подтверждению брони |
| Подтверждение у поставщика | **Асинхронный** | Внешний API отеля/GDS отвечает 5–60 с; HTTP-запрос пользователя нельзя держать |
| Обновление цен и остатков от поставщиков | **Асинхронный** | Поток тысяч событий; Inventory обрабатывает в своём темпе |
| Push / email / SMS | **Асинхронный** | Доставка уведомления не блокирует бизнес-операцию |
| Публикация заказа в личный кабинет маркетплейса | **Асинхронный** | eventual consistency допустима: заказ появится через секунды |
| Возврат средств при отмене | **Асинхронный** | Платёжный провайдер обрабатывает refund 1–5 рабочих дней |
| Напоминание о заезде за 24 ч | **Асинхронный (отложенное)** | Scheduled event в Kafka / отложенная очередь |

### Асинхронные потоки

#### 1. Синхронизация инвентаря от поставщиков [async-flow-01-inventory-sync.png](diagrams/async/async-flow-01-inventory-sync.png)

```
Поставщик → [webhook/polling] → Supplier Integration → Kafka: AvailabilityChanged / PriceUpdated
                                                              ↓
                                                    Inventory & Pricing (consumer)
                                                              ↓
                                                    Catalog (consumer, PropertyUpdated)
```

**Почему async:** channel manager может прислать 10 000 обновлений за минуту в пике. Синхронная запись в Inventory привела бы к каскадным таймаутам у Search. Брокер сглаживает пик; Inventory применяет изменения пакетами. Задержка в несколько секунд между изменением цены у отеля и отображением в поиске — приемлема (eventual consistency).

#### 2. Подтверждение брони у поставщика [async-flow-02-booking-confirmation.png](diagrams/async/async-flow-02-booking-confirmation.png)

```
Booking --[gRPC, sync]--> Supplier Integration --[REST]--> Поставщик
     |                              |
     |  HTTP 202 «принято»          |  (5–30 с)
     ↓                              ↓
  Клиент ← SSE                  Kafka: SupplierConfirmed / SupplierRejected
     ↑                              ↓
     └──────── Booking (consumer) ←─┘
```

**Почему async:** Booking отправляет команду и сразу отвечает клиенту `202 Accepted` + SSE-подписка. Supplier Integration ждёт ответа поставщика в фоне и публикует событие. Booking обновляет статус; клиент получает push через SSE. Если поставщик отклонил — Saga запускает компенсацию: refund через Payment + release hold в Inventory.

#### 3. Уведомления [async-flow-03-notifications.png](diagrams/async/async-flow-03-notifications.png)

```
Booking / Payment → Kafka: BookingConfirmed, BookingCancelled, RefundCompleted
                              ↓
                    Notification (consumer) → push / email / SMS
```

**Почему async:** сбой SMS-шлюза не должен откатить успешную бронь. Notification ретраит доставку независимо; при исчерпании попыток — dead-letter queue для ручного разбора.

#### 4. Callback от платёжного провайдера [async-flow-04-payment-callback.png](diagrams/async/async-flow-04-payment-callback.png)

```
Payment service → [REST webhook] → Payment → Kafka: PaymentSucceeded / PaymentFailed
                                                    ↓
                                              Booking (consumer)
```

**Почему async:** 3-D Secure и рассрочка завершаются вне нашего запроса — провайдер присылает webhook, когда операция завершена. Payment валидирует подпись, публикует событие; Booking продолжает Saga.

#### 5. Отложенные напоминания [async-flow-05-check-in-reminder.png](diagrams/async/async-flow-05-check-in-reminder.png)

```
Booking → Kafka (scheduled topic, delay 24h): CheckInReminder
                    ↓
          Notification → push «завтра заселение»
```

**Почему async:** напоминание — факт в будущем; не нужен cron в Booking — достаточно отложенного сообщения в брокере.

### Что остаётся синхронным и почему

| Участок | Причина |
|---|---|
| Hold / release в Inventory | Атомарность: два параллельных hold на последний номер должны сериализоваться |
| Списание в Payment (первичный вызов) | Пользователь на экране оплаты — ждёт success/fail |
| Поиск и чтение каталога | Данные нужны для рендера UI прямо сейчас |

### Гарантии и компромиссы

- **Доставка:** at-least-once (Kafka) — consumer'ы идемпотентны по `event_id`.
- **Порядок:** события одной брони (`booking_id`) идут в одну партицию Kafka — сохраняется порядок статусов.
- **Консистентность:** асинхронные участки — eventual consistency; пользователь видит промежуточный статус «обрабатывается» до финального «подтверждено».
- **Компенсация:** при сбое на асинхронном шаге Saga откатывает синхронно выполненные шаги (release hold, refund).

## 6. Паттерны

| Паттерн | Где | Зачем |
|---|---|---|
| **Saga (оркестрация)** | Booking | Распределённая транзакция «hold → оплата → подтверждение» без 2PC |
| **CQRS** | Search, Catalog, Inventory | Разделение тяжёлого чтения (поиск) и записи (бронь, hold) |
| **Event-Driven** | Kafka между сервисами | Развязка по времени, буфер пиков, уведомления |
| **BFF** | API Gateway | Единый REST для клиента, агрегация внутренних сервисов |
| **Anti-Corruption Layer** | Supplier Integration | Изоляция разнородных API поставщиков |
| **Идемпотентность** | Booking, Payment | Безопасный retry при сетевых сбоях и дубликатах Kafka |
| **Transactional Outbox** | Booking, Payment | Атомарная запись в БД + публикация события в Kafka |

### Saga (оркестрация) — Booking

**Проблема:** бронирование затрагивает Inventory (hold), Payment (списание) и Supplier Integration (подтверждение). Классическая ACID-транзакция через три сервиса невозможна.

**Решение:** Booking — оркестратор Saga. Последовательность:

1. `hold` в Inventory → при fail — конец, пользователю «нет мест»
2. `charge` в Payment → при fail — компенсация: `release hold`
3. `confirm` в Supplier Integration → при fail — компенсация: `refund` + `release hold`
4. При успехе — `confirm hold` в Inventory, публикация `BookingConfirmed`

**Почему оркестрация, а не хореография:** сценарий линейный с ветвлением и компенсациями; один сервис (Booking) владеет состоянием Saga и проще отлаживается. Хореография через события усложнила бы отслеживание «на каком шаге застряла бронь».

**Состояния Saga** хранятся в Booking (`pending_payment` → `processing` → `confirmed` / `rejected` / `cancelled`).

### CQRS — разделение чтения и записи

**Проблема:** поиск — read-heavy (тысячи RPS, сложные фильтры и ранжирование); бронирование — write-heavy с жёсткой консистентностью. Одна модель и одна БД для обоих сценариев создаёт contention.

**Решение:**
- **Write-модель:** Inventory (hold, confirm), Booking (заказ), Payment (транзакции) — источник истины, оптимизированы под запись.
- **Read-модель:** Search агрегирует снимки из Catalog (статика) и Inventory (цены, остатки) в момент запроса; не пишет в чужие хранилища.

**Eventual consistency на read-пути:** обновление цены у поставщика попадает в Inventory через Kafka с задержкой в секунды — для поиска это допустимо. Hold и бронь работают с актуальным write-слоем Inventory синхронно.

**Полноценный read-replica / проекция** (отдельная БД для Search) можно добавить при росте нагрузки; на текущем масштабе достаточно gRPC-чтений с кэшем.

### Event-Driven Architecture

**Проблема:** жёсткая синхронная связка «Booking вызвал Notification — Notification упал — откатить бронь?» недопустима.

**Решение:** после ключевых переходов состояния Booking и Payment публикуют события в Kafka. Потребители (Notification, контур заказов маркетплейса, Inventory) подписаны независимо.

**Гарантии:** at-least-once + идемпотентные consumer'ы; партиционирование по `booking_id` для порядка событий одной брони.

### BFF (Backend for Frontend)

**Проблема:** клиенту не нужно знать про 7 внутренних сервисов и их протоколы.

**Решение:** API Gateway (BFF) — единая точка входа REST. Агрегирует `GET /search` из Search + Catalog + Inventory, проксирует команды в Booking. Внутри — gRPC; снаружи — REST + SSE.

### Anti-Corruption Layer — Supplier Integration

**Проблема:** у каждого поставщика свой формат (XML GDS, JSON channel manager, SOAP отеля). Подмешивать это в Booking или Inventory размоет доменную модель.

**Решение:** Supplier Integration переводит внешние контракты во внутренние события (`AvailabilityChanged`) и команды (`confirm booking`). Booking знает только `supplier_id` и `supplier_confirmation_id`.

### Идемпотентность

**Где:** `Idempotency-Key` в заголовке для `POST /bookings`, `POST /payments/charge`, `POST /refund`; дедупликация Kafka-событий по `event_id`.

**Зачем:** retry на клиенте, повторная доставка сообщений брокером и таймауты gRPC не должны создавать двойную бронь или двойное списание.

### Transactional Outbox

**Проблема:** нужно атомарно «сохранить бронь в БД» и «опубликовать `BookingConfirmed` в Kafka». Прямая публикация после commit — риск: crash между commit и publish → событие потеряно.

**Решение:** событие пишется в outbox-таблицу в той же транзакции, что и бронь; отдельный relay-процесс читает outbox и публикует в Kafka. Гарантия: событие не потеряется.

### Что сознательно не применяем

| Паттерн | Причина |
|---|---|
| **2PC / распределённые транзакции** | блокировки, низкая доступность; Saga с компенсацией достаточна |
| **Event Sourcing** | избыточен для ДЗ; audit trail решается логами и статусами в Booking |
| **Circuit Breaker на каждом ребре** | актуален для Supplier Integration (внешние API); для внутренних gRPC — на уровне mesh/infra |
