## Выбранная архитектура

Видеостриминг: YouTube

Система позволяет осуществлять загрузку видео и его просмотр  пользователями платформы. Так же система подразумевает ведение и просмотр live контента.
Основными актороми системы являются зрители/потребители контента и авторы контента.
К ключевым сценариям использования относятся: 
- Просмотр видеопотока по поиску и рекоммендациям: пользлватель вводит запрос в поисковой строке вводит, или просто открывает главную страницу и смотрит видео из ленты рекомендаций. Помимо просмотра, можно оставлять комментарии и система лайков;
- Ведение контентмейкером прямых трансляций(стримов): подключается к трансляции, происходит взаимодействует с ведущим и другими зрителями в чате в реальном времени;   
- Загрузка собственного контента для ведения собственного канала.
Количество пользователей: около 2.5 млрд;
Количество пользователей/день: около 300 млн;
Объём данных: около 1 млн ТБ;
RPS: 176_000.
Таким образом можно выделить следующие функциональные требования к системе: загрузка видео, воспроизведение видео, взаимодействие с контентом, управление каналом (для авторов), поддержка стриминга.
К нефунциональным, в свою очередь, относятся: масштабируемость, производительность, доступность, эффективность хранения и передачи данных.


# 1. Компоненты

Ниже — **10 компонентов** backend-части (клиентские приложения и браузер вынесены в акторов из контекста системы). Разделение следует типовой схеме видеостриминга: приём и API отдельно от тяжёлой обработки и раздачи контента.

**Балансировщик нагрузки**  
Тип: балансировщик  
Зона ответственности: распределяет входящие HTTP/gRPC-запросы между экземплярами API-серверов, снимает пики нагрузки с одной машины.

**API-серверы**  
Тип: сервис  
Зона ответственности: приём загрузок, выдача presigned URL, CRUD метаданных (название, описание, статус), авторизация, оркестрация пайплайна «загрузка → обработка → публикация».

**БД метаданных**  
Тип: БД  
Зона ответственности: долговременное хранение метаданных видео, каналов, пользователей, статусов обработки, ссылок на объекты в хранилищах.

**Кэш метаданных**  
Тип: кэш  
Зона ответственности: ускорение частых чтений (карточка видео, статус, счётчики) и снижение нагрузки на БД метаданных.

**Хранилище исходного видео**  
Тип: объектное хранилище  
Зона ответственности: приём и хранение загруженного автором исходного файла до и во время перекодирования.

**Серверы перекодирования**  
Тип: сервис (воркеры)  
Зона ответственности: асинхронное преобразование исходника в набор форматов и битрейтов (адаптивный стриминг), нарезка на сегменты.

**Хранилище перекодированного видео**  
Тип: объектное хранилище  
Зона ответственности: хранение готовых сегментов и манифестов (HLS/DASH) для последующей раздачи через CDN.

**CDN**  
Тип: CDN  
Зона ответственности: раздача видеосегментов и статики зрителям с edge-узлов, ближе к пользователю, снижение latency и нагрузки на origin.

**Очередь завершения**  
Тип: очередь сообщений  
Зона ответственности: буфер событий «перекодирование завершено» — отвязывает воркеры от синхронного обновления метаданных и выдерживает всплески.

**Обработчик завершения**  
Тип: сервис (consumer)  
Зона ответственности: читает события из очереди, обновляет статус видео в БД, инвалидирует кэш, инициирует публикацию в CDN/origin.

# 2. Потоки данных

## 1. Просмотр видео

**Путь запроса.** Зритель открывает страницу видео в клиенте. Сначала клиент запрашивает метаданные (название, описание, URL манифеста, доступные качества) через API; затем воспроизведение идёт напрямую с CDN — тяжёлый трафик не проходит через API. CDN отдаёт манифест и сегменты; при промахе кэша edge-узел подтягивает данные из хранилища перекодированного видео (origin).

**Компоненты:**

1. Клиент (браузер / приложение)
2. Балансировщик нагрузки
3. API-серверы
4. Кэш метаданных → при промахе **БД метаданных**
5. Клиент → **CDN** (манифест HLS/DASH и видеосегменты)
6. CDN → при промахе **Хранилище перекодированного видео**

**Пошаговое описание процесса:**

1. Клиент (браузер или мобильное приложение) отправляет запрос на просмотр видео.
2. Запрос попадает на балансировщик нагрузки, который распределяет нагрузку между серверами для оптимальной производительности.
3. Балансировщик направляет запрос на один из серверов API — они обрабатывают запросы и координируют взаимодействие между компонентами системы.
4. Серверы API обращаются к кэшу метаданных за служебной информацией о видео (название, длительность, доступные разрешения и т. д.):
   - если данные есть в кэше (успешный кэш-хит) — они сразу возвращаются;
   - если данных в кэше нет (кэш-промах) — система обращается к базе данных метаданных, получает информацию и (опционально) сохраняет её в кэш для будущих запросов.
5. Получив метаданные, клиент запрашивает у сети доставки контента (CDN):
   - **манифест HLS/DASH** — файл-плейлист, описывающий структуру видеопотока (где найти сегменты, какие есть варианты качества);
   - **видеосегменты** — небольшие части видео (обычно 2–10 секунд), которые передаются последовательно для потокового воспроизведения.
6. Если нужных данных (манифеста или сегментов) нет в CDN (промах в кэше CDN):
   - CDN запрашивает их из хранилища перекодированного видео (основного централизованного хранилища);
   - полученные данные CDN сохраняет у себя (для ускорения будущих запросов) и передаёт клиенту.
7. Клиент получает манифест и видеосегменты, воспроизводит видео в плеере, при необходимости динамически меняя качество (в зависимости от скорости интернета).

**Сбои на ключевых шагах:**

| Шаг | Сбой | Поведение |
|-----|------|-----------|
| API / балансировщик | недоступен экземпляр | балансировщик направляет на другой API; клиент retry |
| Кэш метаданных | недоступен | API читает из БД (fallback, выше latency) |
| БД метаданных | недоступна | ошибка пользователю («видео недоступно»), без метаданных воспроизведение не стартует |
| CDN | edge недоступен | клиент переключается на другой edge / PoP; retry сегмента |
| Origin (хранилище) | недоступен при cache miss | CDN не отдаёт сегмент → буферизация, снижение качества или ошибка воспроизведения |

## 2. Загрузка видео

**Путь запроса.** Автор через API получает presigned URL и загружает исходник в хранилище. Серверы перекодирования асинхронно кодируют файл и публикуют сегменты в CDN. Затем событие уходит в очередь завершения: обработчик переводит статус в БД и сбрасывает кэш метаданных — после этого видео доступно зрителям (сценарий 1).

**Компоненты:**

1. Клиент → Балансировщик → API-серверы (создание записи, presigned URL)
2. API → Хранилище исходного видео (статус «обрабатывается»)
3. **Серверы перекодирования** (читают исходник, пишут сегменты)
4. Сервер перекодирования -> публикация в **CDN**
5. Перекодирование завершено -> **Очередь завершения** → **Обработчик завершения**
6. Обработчик завершения → **БД метаданных**, инвалидация **Кэша метаданных**

**Пошаговое описание процесса:**

1. Клиент (автор) инициирует загрузку видео через браузер или приложение.
2. Запрос проходит через балансировщик нагрузки и попадает на один из API-серверов.
3. API-серверы создают запись о новом видео и выдают клиенту presigned URL для прямой загрузки файла.
4. API регистрирует видео в **хранилище исходного видео** со статусом «обрабатывается»; клиент по presigned URL загружает исходный файл в это хранилище (минуя API-серверы).
5. **Серверы перекодирования** автоматически обнаруживают новый файл и запускают асинхронный пайплайн: читают исходник из хранилища, создают версии в разных разрешениях и битрейтах, формируют видеосегменты.
6. **Серверы перекодирования** публикуют готовые манифест HLS/DASH и сегменты в **CDN**, чтобы зрители могли получать контент с edge-узлов.
7. По завершении перекодирования система формирует событие и помещает его в **очередь завершения**; **обработчик завершения** забирает событие из очереди.
8. **Обработчик завершения** обновляет статус видео в **БД метаданных** на «доступно» и инвалидирует устаревшие данные в **кэше метаданных**.
9. Видео доступно для просмотра зрителями через CDN.

**Синхронность:**

| Участок | Режим |
|---------|--------|
| Запрос upload URL, запись метаданных | синхронный |
| Загрузка файла в object storage | синхронный (multipart; долгий, но без удержания API) |
| Перекодирование | асинхронный (фоновые воркеры) |
| Очередь + обработчик завершения | асинхронный |

**Сбои на ключевых шагах:**

| Шаг | Сбой | Поведение |
|-----|------|-----------|
| Загрузка в storage | обрыв сети | клиент resume multipart upload |
| Перекодирование | падение воркера | retry задачи из очереди заданий; статус остаётся «обрабатывается» |
| Очередь | недоступна | воркеры буферизуют или откладывают публикацию; видео не появляется в ленте до восстановления |
| Обработчик | сбой при обновлении БД | повторная обработка сообщения (at-least-once); идемпотентное обновление статуса |

## 3. Live-стриминг

Сценарий объединяет два потока: **ведение эфира** (автор, по аналогии с загрузкой — ingest и публикация в CDN) и **просмотр трансляции** (зритель, по аналогии с просмотром VOD — метаданные через API, поток с CDN).

**Путь запроса.** Автор через API получает stream key и URL ingest, в БД создаётся запись эфира со статусом «в эфире». Поток непрерывно идёт на серверы перекодирования, которые пакуют короткие сегменты и сразу публикуют их в CDN. Зритель запрашивает метаданные трансляции (как в сценарии 1), затем плеер периодически обновляет live-манифест и тянет свежие сегменты с CDN. После остановки эфира событие попадает в очередь завершения; обработчик обновляет БД и кэш (статус «завершено»), при необходимости запись архивируется в хранилище.

**Компоненты:**

*Ведение эфира (автор):*

1. Клиент (автор) → Балансировщик → API-серверы (создание эфира, stream key, URL ingest)
2. API → **БД метаданных**, **кэш метаданных** (статус «в эфире»)
3. Клиент (автор) → **Серверы перекодирования** (непрерывный ingest RTMP/WebRTC)
4. **Серверы перекодирования** → публикация live-сегментов и манифеста в **CDN**

*Просмотр трансляции (зритель):*

5. Клиент (зритель) → Балансировщик → API → кэш / **БД метаданных**
6. Клиент (зритель) → **CDN** (live-манифест HLS/DASH и сегменты)
7. CDN → при промахе **хранилище перекодированного видео** (кратковременный буфер origin для live)

*Завершение эфира:*

8. Остановка ingest → **Очередь завершения** → **Обработчик завершения**
9. Обработчик → **БД метаданных**, инвалидация **кэша метаданных**

**Пошаговая визуализация процесса**

**Часть 1. Автор начинает трансляцию:**

- Клиент (автор) → Балансировщик → API-серверы: запрос на создание эфира.
- API-серверы:
  - создают запись в БД метаданных (статус «в эфире»);
  - обновляют кэш метаданных;
  - выдают stream key и URL ingest.
- Автор направляет поток на серверы перекодирования (RTMP/WebRTC).
- Серверы перекодирования:
  - нарезают поток на сегменты (2–4 с);
  - формируют live-манифест;
  - публикуют в CDN.

- Клиент (зритель) → балансировщик → API: запрос метаданных.
- API читает из кэша метаданных (при промахе — из БД).

  - запрашивает live-манифест и видеосегменты;
  - при промахе кэша CDN подтягивает сегмент из хранилища перекодированного видео.
- Плеер зрителя обновляет манифест и догружает сегменты.

- Событие попадает в очередь завершения.
- Обработчик завершения:
  - обновляет статус в БД метаданных на «завершено»;
  - инвалидирует кэш метаданных;
  - опционально сохраняет запись в хранилище для просмотра как VOD.

**Пояснения к компонентам:**

- **Stream key** — уникальный ключ потока для авторизации автора.
- **URL ingest** — адрес для отправки видеопотока от кодера (OBS и т. д.).
- **Live-манифест (HLS/DASH)** — динамически обновляемый плейлист, описывающий доступные сегменты эфира.
- **Буфер origin** — кратковременное хранилище сегментов на случай промаха кэша CDN.
- **Инвалидация кэша** — принудительное удаление устаревших данных из кэша для актуализации информации.

**Синхронность:**

| Участок | Режим |
|---------|--------|
| Создание эфира, stream key, метаданные для зрителя | синхронный |
| Ingest автор → серверы перекодирования | непрерывный поток (длительное соединение) |
| Упаковка сегментов → CDN | асинхронный конвейер (сегменты с задержкой 2–10 с от «живого» момента) |
| Просмотр: клиент ↔ CDN | синхронные GET; периодический poll/обновление live-манифеста |
| Завершение эфира → очередь → обработчик | асинхронный |


**Сбои на ключевых шагах:**

| Шаг | Сбой | Поведение |
|-----|------|-----------|
| API / балансировщик | недоступен | retry; без stream key автор не начнёт эфир |
| Ingest | обрыв у автора | reconnect с тем же stream key; краткий blackout у зрителей |
| Перекодирование | перегрузка | снижение качества или отказ новых зрителей; предупреждение автору |
| CDN | деградация edge | зритель переключается на другой PoP; retry сегмента |
| Отставание конвейера | сегменты запаздывают | увеличение buffer у плеера или сообщение «трансляция отстаёт» |
| БД / кэш (зритель) | недоступны | как в сценарии 1: fallback кэш→БД; без метаданных просмотр не стартует |
| Очередь / обработчик при завершении | сбой | повторная обработка события; статус эфира может временно не обновиться |


## 3. Проблемы и решения


### Балансировщик нагрузки

**Какую проблему решает:** при ~176 000 RPS и сотнях миллионов DAU один API-инстанс не выдержит входящий поток; нужна равномерная раздача запросов по пулу серверов.

**Без него:** узкое горлышко на одном хосте, рост latency и отказов при пиках (прайм-тайм, премьеры).

**Trade-offs:** выигрыш — горизонтальное масштабирование API; жертва — дополнительный hop, сложность health-check и sticky-сессий там, где они нужны.

**Масштабирование:** добавление API-инстансов за балансировщиком (scale-out).

**Надёжность:** исключение «больного» инстанса из пула; DNS/anycast на несколько балансировщиков.

### API-серверы

**Какую проблему решает:** единая точка оркестрации — авторизация, метаданные, presigned URL, stream key; клиент не знает внутреннюю топологию хранилищ и воркеров.

**Без него:** нет согласованного контракта для клиентов; загрузка и просмотр нельзя безопасно и предсказуемо связать с объектами в storage.

**Trade-offs:** выигрыш — простой клиентский API; жертва — риск превратить API в «god service», поэтому тяжёлые байты (файл, сегменты) идут мимо API (presigned URL, CDN).

**Масштабирование:** stateless-реплики за балансировщиком.

**Надёжность:** retry на уровне клиента и LB; деградация отдельных инстансов без остановки всего сервиса.

### БД метаданных

**Какую проблему решает:** источник истины для названий, статусов («обрабатывается», «доступно», «в эфире»), ссылок на объекты в storage и CDN.

**Без него:** невозможно найти видео, показать карточку, отличить «ещё кодируется» от «готово к просмотру».

**Trade-offs:** выигрыш — ACID и сложные запросы по метаданным; жертва — при миллиардах записей нужны шардирование и репликация, БД не держит видеобайты.

**Масштабирование:** шардирование по `video_id` / `channel_id`; read-реплики для чтения карточек.

**Надёжность:** репликация master–replica; без БД просмотр не стартует (см. таблицы сбоев в потоках).

### Кэш метаданных

**Какую проблему решает:** карточка видео и статус читаются на каждый просмотр; без кэша БД утонет в read-нагрузке при 300 млн DAU.

**Без него:** latency метаданных растёт, БД — первое узкое место при viral-роликах.

**Trade-offs:** выигрыш — скорость и разгрузка БД; жертва — eventual consistency, нужна инвалидация при смене статуса (обработчик после загрузки/live).

**Масштабирование:** кластер кэша, шардирование ключей по `video_id`.

**Надёжность:** fallback API → БД при недоступности кэша (описано в сценарии просмотра).

### Хранилище исходного видео

**Какую проблему решает:** приём больших файлов (до гигабайт) и хранение «как загрузил автор» до перекодирования; отделение write-heavy upload от API.

**Без него:** некуда положить исходник; перекодированию нечего читать.

**Trade-offs:** выигрыш — дешёвое масштабируемое object storage, multipart upload; жертва — высокая стоимость хранения сырья, дублирование с перекодированными копиями.

**Масштабирование:** партиционирование бакетов, географическое размещение ближе к ingest.

**Надёжность:** репликация объектов, resume multipart при обрыве загрузки.

### Серверы перекодирования

**Какую проблему решает:** единый формат для плеера (HLS/DASH, несколько битрейтов); исходник в произвольном кодеке/разрешении нельзя отдавать напрямую миллиардам клиентов.

**Без него:** нет адаптивного стриминга, нет совместимости устройств, огромный исходный трафик с origin.

**Trade-offs:** выигрыш — качество под сеть зрителя; жертва — CPU/GPU дороги, задержка от загрузки до «доступно» (минуты–часы для VOD, 2–10 с для live).

**Масштабирование:** пул воркеров, очередь задач кодирования, автоскейл по длине очереди.

**Надёжность:** retry задачи при падении воркера; статус в БД остаётся «обрабатывается» до успеха.

### Хранилище перекодированного видео

**Какую проблему решает:** долговременное хранение сегментов и манифестов; origin для CDN при cache miss и буфер для live.

**Без него:** CDN нечем наполнять при промахе; нет архива сегментов между edge и «сырьём».

**Trade-offs:** выигрыш — предсказуемый origin; жертва — объём ~1 млн ТБ, стоимость хранения и egress в CDN.

**Масштабирование:** lifecycle policies (редкие ролики в cold tier), шардирование по префиксам объектов.

**Надёжность:** репликация объектов; при недоступности origin — буферизация/ошибка у зрителя (сценарий просмотра).

### CDN

**Какую проблему решает:** ~99% трафика просмотра — видеосегменты; отдавать их из одного дата-центра нельзя ни по latency, ни по bandwidth (масштаб YouTube).

**Без него:** глобальная задержка, перегруз origin, невозможность обслужить сотни миллионов одновременных просмотров.

**Trade-offs:** выигрыш — низкий RTT, кэш на edge; жертва — стоимость CDN, сложность инвалидации, eventual consistency кэша на edge.

**Масштабирование:** географически распределённые PoP; популярный контент «размазывается» по edge без роста нагрузки на API.

**Надёжность:** переключение на другой PoP, retry сегмента; origin fetch при miss.

### Очередь завершения

**Какую проблему решает:** декуплинг «перекодирование закончилось» и «обновить метаданные»; сглаживание всплесков событий после массовых загрузок и окончания эфиров.

**Без него:** воркеры синхронно бьют в БД → contention; при пике — потери событий или таймауты.

**Trade-offs:** выигрыш — буфер и backpressure; жертва — задержка появления статуса «доступно» в UI, at-least-once семантика.

**Масштабирование:** партиционирование топика по `video_id`, несколько consumer-групп.

**Надёжность:** очередь как буфер при недоступности БД/обработчика; повторная доставка сообщений.

### Обработчик завершения

**Какую проблему решает:** атомарное с точки зрения бизнеса завершение пайплайна — статус в БД, свежий кэш, согласованность «CDN уже отдаёт, в каталоге видно».

**Без него:** видео в CDN, но в ленте «обрабатывается»; рассинхрон кэша и БД.

**Trade-offs:** выигрыш — централизованная логика постобработки; жертва — отдельный сервис, идемпотентность обработки, мониторинг lag очереди.

**Масштабирование:** несколько consumer-инстансов (при идемпотентных обновлениях).

**Надёжность:** повторная обработка события; идемпотентное обновление статуса.

### Архитектурные решения (связка компонентов)

| Решение | Проблема | Без него | Trade-off | Масштабирование | Надёжность |
|---------|----------|----------|-----------|-----------------|------------|
| Прямая загрузка в storage (presigned URL) | API не должен проксировать гигабайты | API падает от bandwidth, дорогой double-hop | Сложнее клиент, зато API лёгкий | Upload масштабируется storage, не API | Multipart resume |
| Разделение API-пути и CDN-пути просмотра | 176k RPS метаданных ≠ петабайты видео в секунду | API или origin рухнут от сегментов | Два канала в клиенте | CDN + edge cache | Fallback origin |
| Асинхронное перекодирование + очередь | Upload быстрее, чем encode | Автор ждёт часами на HTTP-соединении | Задержка публикации | Воркеры scale-out | Retry, буфер очереди |
| Два хранилища (исходник / сегменты) | Разный lifecycle и стоимость | Смешение сырья и CDN-объектов в одном бакете | Дороже storage, проще операции | Cold tier для исходников | Независимые SLA |

## 4. Вопросы к авторам архитектуры

1. **Почему публикация в CDN идёт с серверов перекодирования, а не через обработчик завершения?** В схеме загрузки сегменты появляются на CDN до события в очереди. Как гарантируется, что зритель не получит сегменты раньше, чем статус в БД станет «доступно» — feature flag, версионирование манифеста или задержка в CDN?

2. **По какому ключу шардируется БД метаданных при 2.5 млрд аккаунтов и миллиардах видео?** Достаточно ли шардирования по `channel_id`, или горячие каналы (музыка, новости) требуют отдельного разбиения / выноса счётчиков в отдельное хранилище?

3. **Какой TTL и стратегия инвалидации у кэша метаданных для viral-видео?** При взрывном росте просмотров не упрётся ли read-реплики БД в промахи кэша; используется ли proactive warming при тренде?

4. **Где граница между live и VOD в одном пайплайне перекодирования?** Один пул воркеров на ingest и batch encode — не станет ли live жертвой очереди длинных VOD-файлов; есть ли приоритетные очереди?

5. **Что происходит с исходниками в хранилище после успешного перекодирования?** Удаляются сразу, через N дней или хранятся для re-encode — какой trade-off стоимости ~1 млн ТБ против возможности смены кодеков?
